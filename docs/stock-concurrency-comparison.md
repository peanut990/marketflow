# 재고 차감 전략 비교: 낙관적 락 vs Atomic UPDATE

## 비교 목적

Day 3의 목표는 더 많은 기능을 구현하는 것이 아니라, 같은 주문 경합 조건에서 낙관적 락과 Atomic UPDATE의 장단점이 어떻게 드러나는지 확인하는 것이다.

비교 대상은 다음과 같다.

```text
낙관적 락: 8672a3b 기준, @Version + 주문 생성 retry + random backoff
Atomic UPDATE: test/atomic-update 기준, 조건부 UPDATE + affected rows 확인
```

실행 시간은 로컬 MySQL 테스트 DB와 JVM/스레드 스케줄링 영향을 받으므로 절대 성능값이 아니라 비교 관찰값으로 본다.

- 최종 재고는 `initialStock - success`와 같다.
- 최종 재고는 음수가 되지 않는다.
- `orders`, `orderItems`, `cartItems` 수가 성공/실패 수와 일치한다.
- `unexpectedFailure`는 0이다.

## 낙관적 락

낙관적 락은 엔티티에 `@Version`을 두고, 커밋 시점에 version 조건이 맞지 않으면 충돌로 감지한다. 충돌이 발생하면 주문 생성 전체를 새 트랜잭션에서 다시 실행한다.

장점은 도메인 로직을 엔티티 중심으로 유지하기 쉽다는 점이다. 재고 차감 외에도 여러 엔티티 상태 변경이 자연스럽게 묶여 있고, 충돌이 낮은 상황에서는 별도의 DB 락 대기 없이 진행할 수 있다.

단점은 경합이 늘어날수록 충돌과 retry 비용이 커진다는 점이다. 이번 실행에서는 1000/1000처럼 재고가 충분한데도 343건이 retry 10회를 모두 소진해 실패했다. 사용자는 실제로 주문 가능한 재고가 남아 있었는데도 실패 응답을 받을 수 있고, 애플리케이션은 실패한 시도마다 트랜잭션을 새로 열고 조회/검증/차감을 반복한다.

## Atomic UPDATE

Atomic UPDATE는 재고 확인과 차감을 하나의 조건부 UPDATE로 처리한다.

```sql
UPDATE product_options
SET stock_quantity = stock_quantity - ?
WHERE id = ?
  AND active = true
  AND stock_quantity >= ?
```

장점은 단순 재고 차감에서 성공/실패 판단이 명확하다는 점이다. affected rows가 1이면 차감 성공이고, 0이면 차감 실패다. 낙관적 락처럼 주문 생성 전체 retry와 backoff가 필요하지 않으며, 1000/1000 시나리오에서도 재고가 충분한 만큼 모두 성공했다.

단점은 영속성 컨텍스트와 DB 상태가 어긋날 수 있다는 점이다. JPQL update는 엔티티 변경 감지가 아니라 DB에 직접 UPDATE를 실행하므로, 같은 트랜잭션에서 이미 로딩된 `ProductOption`의 재고 값을 다시 신뢰하면 안 된다. 또한 재고 차감 외의 복잡한 도메인 상태 전이를 모두 SQL 조건으로 표현하기는 어렵다. 현재 구현은 cartItem별 row 단위 조건부 UPDATE라, 여러 옵션을 주문하면 옵션 수만큼 UPDATE가 실행된다.

## MarketFlow 선택

현재 MarketFlow의 주문 생성에서는 Atomic UPDATE를 기본 재고 차감 전략으로 둔다.

선택 이유는 현재 도메인의 핵심 경합 지점이 상품 옵션 재고의 단순 감소이기 때문이다. 이 경우 DB의 조건부 UPDATE와 InnoDB row lock, affected rows 확인만으로 과판매 방지와 실패 분류를 설명할 수 있다. 낙관적 락보다 retry/backoff 정책이 단순하고, 충분한 재고가 있는 경합에서 retry 소진으로 실패할 가능성도 줄일 수 있다.

낙관적 락은 여러 엔티티 변경을 엔티티 중심으로 유지해야 하고 충돌이 낮은 업무에 적합한 후보로 남긴다. 비관적 락은 재고 외 상태까지 반드시 순차 처리해야 하거나, 실패보다 대기가 더 나은 업무에서 비교 대상으로 남긴다.
